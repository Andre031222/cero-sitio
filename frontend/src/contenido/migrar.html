Migrar

Llevar una aplicación a Cero 0.6.0, venga de LuxCore 0.2.x/0.3.x o de Corvo 0.4.0. El guion hace casi todo; hay tres cosas que no puede hacer y que se notan después de desplegar.

01

No hay prisa

Las aplicaciones que no migres siguen funcionando. Los artefactos de Maven son inmutables: lux:lux-core:0.3.0 sigue en tu ~/.m2 y dentro de cada jar desplegado. Renombrar el framework no entra ahí a cambiar nada.

Puedes migrar una, dejar las otras cinco meses como están, y no pasa nada. La etiqueta v0.3.0 del repositorio sigue ahí: si algún día hay que recompilar una aplicación vieja en una máquina limpia, ./lux install desde esa etiqueta regenera los artefactos antiguos.

Cómo hacerlo

De una en una. Con producción de por medio, esa es la forma de que un problema afecte a una sola aplicación y no a seis.

02

Antes de tocar nada

1 · Instala Cero 0.6.0

En el repositorio de Cerosh
./cero install          # compila, prueba e instala en ~/.m2

2 · Deja limpio el árbol de git de la aplicación

En tu aplicaciónsh
cd ../mi-app
git status               # no debe quedar nada sin guardar

El guion se niega a correr si hay cambios sin guardar, y es a propósito: así el propio git es la copia de seguridad. git diff enseña todo lo que tocó y git checkout . lo deshace entero. No hace falta andar copiando carpetas.

3 · Renombra la tabla de migraciones

Esto va antes de arrancar la aplicación

Si tu aplicación usa Migrations de cero-data, para y lee. El framework anota en una tabla qué migraciones ya se aplicaron. Se llamaba lux_migraciones y ahora se llama cero_migraciones. Si arrancas sin renombrarla, Cero no la encuentra, da por hecho que no se aplicó ninguna y las vuelve a correr todas.

Eso no falla al compilar. Falla contra tu base de datos.

Antes de arrancarSQL
ALTER TABLE lux_migraciones RENAME TO cero_migraciones;

Lo mismo con la tabla de sesiones, si usas JdbcSessions y le dejabas el nombre por defecto:

Solo si usas JdbcSessionsSQL
ALTER TABLE lux_sesiones RENAME TO cero_sesiones;

Si le pasabas un nombre propio —JdbcSessions.of("mis_sesiones")— no tienes que hacer nada.

03

Migrar

En el repositorio de Cerosh
./cero migrar ../mi-app --probar    # enseña qué cambiaría, sin tocar nada
./cero migrar ../mi-app             # lo aplica

Comprobar

En tu aplicaciónsh
cd ../mi-app
git diff                 # revisa lo que cambió
mvn test                 # y que siga pasando
04

Lo que el guion no puede

Tres cosas. Ninguna da error al compilar, y las tres se notan después de desplegar — que es el peor momento para enterarse.

La cookie de sesión cambió de nombre

LUXSESSION pasa a ser CEROSESSION. El navegador de cada usuario sigue mandando la vieja, que la aplicación nueva ya no reconoce.

Consecuencia

Al desplegar, todo el mundo que estuviera dentro tiene que volver a entrar. No se pierde nada, pero conviene desplegar cuando no moleste, y avisar si es una aplicación con gente trabajando.

Las métricas cambiaron de nombre

AntesDespués
lux_requests_totalcero_requests_total
lux_request_errors_totalcero_request_errors_total
lux_request_duration_mscero_request_duration_ms
lux_uptime_mscero_uptime_ms
/lux/metrics/cero/metrics
/lux/metrics/prometheus/cero/metrics/prometheus
Consecuencia

El scrapeo de Prometheus apunta a una ruta que ya no existe, y los paneles de Grafana consultan métricas que dejaron de emitirse. Los paneles no dan error: se quedan vacíos, que es peor, porque parece que la aplicación no recibe tráfico. Hay que actualizar el prometheus.yml y las consultas de los paneles.

La configuración desplegada, no solo la del repositorio

El guion cambia los .properties que estén dentro de la aplicación. Si en el servidor tienes un application.properties aparte, o variables LUX_* en el systemd o en el docker-compose, esas hay que cambiarlas a mano.

En el servidorsh
grep -rn 'LUX_\|lux\.' /etc/systemd/system/mi-app.service /opt/apps/mi-app/
05

Sin capa de compatibilidad

Era la opción evidente: que Cero entendiera los dos nombres durante una temporada. Se descartó a propósito.

Solo seis aplicaciones usan el framework y son todas nuestras. Aceptar los dos prefijos significaría arrastrar código muerto para siempre en un proyecto cuyo argumento es no tener lastre — y en la práctica esas capas no las retira nadie nunca. Convertir seis aplicaciones una vez sale más barato que cargar con la deuda indefinidamente.

06

Si algo sale mal

Deshacersh
git checkout .           # deshace la migración entera

Y en el pom.xml, volver a la versión anterior. Los artefactos viejos siguen en ~/.m2 y la aplicación compila como antes, porque nunca dejaron de existir.

Si ya habías renombrado las tablas y quieres volver atrás del todo:

Volver atrásSQL
ALTER TABLE cero_migraciones RENAME TO lux_migraciones;
ALTER TABLE cero_sesiones RENAME TO lux_sesiones;
07

Repaso

  • ./cero install — Cero 0.6.0 en ~/.m2
  • El árbol de git de la aplicación, limpio
  • ALTER TABLE lux_migraciones RENAME TO cero_migraciones;
  • ALTER TABLE lux_sesiones RENAME TO cero_sesiones; (si aplica)
  • ./cero migrar ../mi-app --probar
  • ./cero migrar ../mi-app
  • git diff y mvn test
  • Configuración del servidor: systemd, docker-compose, los .properties de producción
  • Prometheus y los paneles de Grafana
  • Avisar de que las sesiones se cierran al desplegar
