01

cero-test

It starts the application on a free port, asks it for something with a client that keeps the cookies, and asserts on the response. No dependencies outside the JDK: cero-data and the JDBC driver are optional and only needed for TestDatabase.

Adding itMaven
<dependency>
    <groupId>dev.ginit.cero</groupId>
    <artifactId>cero-test</artifactId>
    <version>0.7.0</version>
    <scope>test</scope>
</dependency>
A whole testJava
try (TestServer app = TestServer.start(MyApplication.app())) {
    TestClient client = app.client();

    client.get("/me").status(401);
    client.form("/login", Map.of("usuario", "ada", "clave", "secreta"))
          .status(302)
          .cookie("CEROSESSION");
    client.get("/me").ok().json("usuario.nombre", "Ada");
}

Two details that change a test

The client does not follow redirects: a successful login answers 302 and that is the response you look at. And the operating system picks the port, so two modules testing in parallel do not collide.

cero.data.Migrations: schema versioned by fingerprint. The name of the control table is configurable, which is worth knowing before pointing two applications at the same database.

What repair() is for

It is the way out for a corrected migration that does not change what it left in the schema. Without it, startup stops in every environment over a fingerprint that no longer matches, and the only remedy is editing the table by hand.

04

Rows

cero.data.Row implements a read-only Map<String, Object>, so that when nested in a response it serialises as a JSON object instead of being introspected through getters. Column lookup is case-insensitive.

Writing into a row no longer compiles the same

The write operations of the Map contract —put, putAll, remove, clear— throw UnsupportedOperationException, and Row.put is no longer public. A row is built with Row.of(…) or Row.from(Map).

05

Configuration

A CERO_* environment variable loses the prefix, goes to lower case and turns _ into .: CERO_SERVER_PORT is server.port. At the end of startup, once everyone has asked, Config warns about the ones that did not end up in any key anybody reads.

SituationWarningWhat happened
There are CERO_* variables and nobody read the environment… no se leen: la aplicación no llama a loadConfig()It names them all, sorted. None of them applied.
The real key is in camelCase… no se aplica: la clave es …, en camelCase, y el entorno no distingue mayúsculasThe translation lowercases, so it never matches the key the application asks for.
Nobody asks for the translated key… no corresponde a ninguna clave conocida (…)A misspelt name, or a key that no longer exists. In brackets, the key the translation produced.
Why it matters

All three used to apply with no effect and in silence: the variable was set, the configuration did not change, and nothing in the log said so.

They inherit from it, so they fell into its branch and were treated as instants: 19:00 was written 1970-01-02T00:00:00Z and dates moved a day forward on the way to UTC. time and date are clock and calendar labels, and now they come out as such.

07

Request parameters

@Query takes the parameter from the query string and @Form from the form body. Both have the same shape.

MemberTypeWhat it does
value()StringName of the parameter. Required.
orElse()StringDefault value when the parameter does not arrive. Defaults to the sentinel.
SIN_DEFECTOStringSentinel for "no default declared": "\u0000cero.sin-defecto".
Correction: orElse = "" now applies the empty string

The sentinel exists precisely because the empty string is a legitimate value. Declaring @Query(value = "q", orElse = "") hands over "" when the parameter is missing; it used to arrive as null. With no orElse declared, the binding is still null.

08

Databases

cero-data speaks JDBC and nothing else. Any engine with a JDBC driver works — the driver comes from your application, which is the only external dependency Cero allows.

EngineStatusNote
H2 2.2VerifiedIn memory and on file. The engine behind the example application and its 43 end-to-end tests.
PostgreSQL 16Verified47 cases in a container: BIGSERIAL, exact decimals, native booleans, dates and LIMIT/OFFSET.
MySQL 8VerifiedThe same 47 cases: AUTO_INCREMENT, booleans over TINYINT and generated keys.
MariaDBNot verifiedShares protocol and dialect with MySQL, so it should behave the same.
SQL ServerNeeds workDoes not support LIMIT/OFFSET: it uses OFFSET … FETCH. Pagination needs an adjustment.
OracleNot verifiedReturns column names in upper case, which is already handled since that bug was fixed.
SQLiteNot verifiedNo write concurrency: the pool should be set to 1.
What "verified" means here

The three engines marked as such pass the same suite of 47 cases, running in containers: generated keys, exact decimals, booleans, dates, pagination, upper-case aliases, committed and rolled-back transactions, repositories and batch inserts. That suite found a real bug —Row.as() ignored @Column and returned null fields— that no test with a mocked driver had caught.

Where it runs

There is no native code and nothing platform-specific. Wherever there is a JDK 25 or newer, it runs the same.

The real requirement
Java 25 as the compilation target; virtual threads, which landed in 21: the server assigns one per connection, and without them the model does not hold up. Developed and measured with OpenJDK 25.
Detecting is not testing
The installer recognises those systems and architectures and knows which command to give on each. Tested, with the whole suite green, is only what is marked above.
No native code
No JNI, no system libraries, no absolute paths. The JAR is the same everywhere.
10

Against the others

All nine in identical containers, 64 connections, 30 seconds, the same -Xmx256m for every one, median of five runs, sorted by boot time. 135 measurements with no errors and no non-2xx responses. Same machine and same data-access class throughout: what is measured is the cost of serving the request, not a choice of ORM or serialiser.

What this table says, and what it does not

It says Cero boots in 87 ms, 4.4 times faster than the runner-up and 17.8 times faster than Spring Boot. No margin of error explains that gap.

And it says Cero uses the most memory of the nine: 332 MB against Vert.x's 104. It is not a leak — RSS plateaus, and with -Xmx96m it serves the same traffic 4% faster in 176 MB — it allocates more per request than the others and fills whatever heap it is given. That is the next thing to fix.

About requests per second it says nothing. The top six land within 2% of each other, while each one's own spread across its five runs ranges from 2.2% to 12.5%. On this measurement, claiming one serves faster than another would be noise. The only real separation is the tail on /db.

What it does not give you is quotable absolute figures: this was measured on Docker Desktop, inside a VM. The conditions were identical for all five, so the comparison is fair; the individual numbers need repeating on bare metal before they go anywhere.
