01

Routes

@Route on the class sets the base; the verbs on the methods add the rest. One rule, no exceptions: an empty value maps to the base route.

AnnotationResulting routeNote
@Route("/api/tareas")/api/tareasClass base
@Get/api/tareasEmpty value = the base
@Get("/{id}")/api/tareas/{id}Route variable
@Get("/{id}/notas/{n}")…/{id}/notas/{n}Several variables
@Get("/archivos/*")/api/tareas/archivos/*Wildcard, only at the end
@Post @Put @Patch @Delete—Same criteria
  • Literal beats variable. /tareas/nueva resolves before /tareas/{id}, whatever order they are declared in.
  • Without @Route, the base comes from the class name: ReporteController → /reporte.
  • Duplicate routes fail at startup, not on the first request.
  • 405 with Allow. If the route exists but the verb does not, the response lists the valid verbs.
  • HEAD resolves against GET automatically, with no body.

Loose routes, with no controller

LambdasJava
.routes(r -> r
    .get("/salud", ctx -> "ok")
    .get("/version", ctx -> Map.of("version", "0.7.0"))
    .post("/eco", ctx -> ctx.bodyText()))

Method arguments are resolved by annotation or by type. Conversion to int, long, boolean, enums or dates is automatic; if the value does not convert, the response is a 400.

This is a behaviour change in 0.7.0: the empty string used to be the sentinel for «no default declared» and that parameter arrived null, so a search filter written that way blew up with a NullPointerException on the first visit. Injection

Mark a service with @Service and it is built the first time somebody asks for it. Controllers receive it with @Inject, by field or by constructor.

ServicesJava
@Service
public class Catalogo {
    @Inject Repositorio repositorio;      // by field
}

@Service
public class Facturas {
    private final Catalogo catalogo;
    @Inject Facturas(Catalogo catalogo) {   // by constructor
        this.catalogo = catalogo;
    }
}

// or by hand, handy for swapping in tests
Cero.app().service(Reloj.class, () -> Instant.now())
  • Services are singletons: one instance per application.
  • They are also registered under their interfaces, so you can ask for the contract.
  • Circular dependencies are detected and the error names the whole chain.

Errors

Throw HttpException with whatever status you want, or register a handler with @OnError for an exception from your own domain.

Error handlingJava
@Get("/{id}")
public Object ver(@Path("id") long id) {
    Tarea t = tareas.findById(id);
    if (t == null) throw new HttpException(404, "no existe la tarea " + id);
    return t;
}

@OnError(SaldoInsuficiente.class)
public Object saldo(SaldoInsuficiente fallo) {
    return Result.json(Map.of("motivo", fallo.getMessage())).status(422);
}
Uncaught exceptions never leak details

Any exception that is not an HttpException returns a 500 with the generic message "error interno". The stack trace goes to the ErrorReporter, not to the response.

07

Optional base class

A Cero controller inherits from nothing: it is an ordinary class with annotations, and the Context arrives as a parameter when it is needed. If a controller uses it in nearly every method, you can extend Controller and save yourself the trouble.

With the base classJava
@Route("/panel")
public class PanelController extends Controller {

    @Get("/perfil")
    public Result perfil() {
        if (!autenticado()) return redirect("/auth/login");
        return view("perfil", Map.of("usuario", usuario().name()));
    }

    @Get("/informe/{id}")
    public Result informe() {
        var informe = informes.porId(param("id"));
        if (informe == null) throw fallo(404, "no existe");
        return json(informe);
    }
}

It brings param, query, form, header, cookie, body, session, usuario, autenticado, and on the response side view, json, text, html, redirect, created, noContent, status and fallo. For everything else, ctx() returns the whole Context.

It really is optional. Both styles live side by side in the same application: whoever does not extend it keeps receiving the Context as a parameter and never learns this exists.

Why it does not keep the request in a field

There is a single instance of the controller, shared by every request, and Cero serves each connection on its own virtual thread. A field holding the request would be a race: two simultaneous requests would overwrite it and one would end up answering with the other's data. That is why the helpers read from a per-thread holder. There is a test that fires 200 simultaneous requests and checks that each response carries its own data; with a shared field, it fails.

Sessions and access

The session is requested from the context. It is born the first time it is used, and the cookie goes out HttpOnly, SameSite=Lax and Secure if the request came over HTTPS.

SessionJava
Session sesion = ctx.session();
sesion.set("usuario", correo);
String quien = sesion.get("usuario", String.class);
sesion.invalidate();                     // on sign-out
Rotate the identifier when signing in

The identifier a visitor holds before signing in cannot stay valid afterwards: whoever had planted it in their browser would end up with an authenticated session. That is session fixation, and one line avoids it: 

if (Passwords.matches(clave, usuario.hash())) {
    ctx.session().regenerateId();        // ← right here, before storing anything
    ctx.session().set("usuario", usuario.correo());
}

It preserves the contents —including the CSRF token— unlike invalidate(), which wipes everything.

Passwords are stored with Passwords: PBKDF2-HMAC-SHA256 at 210,000 iterations, a per-password salt and constant-time comparison. The format carries the cost inside, so it can be raised without invalidating what is already stored.

PasswordsJava
String guardado = Passwords.hash(clave);
boolean vale = Passwords.matches(clave, guardado);
if (Passwords.needsRehash(guardado)) {   // the cost went up since it was stored
    usuarios.actualizarHash(id, Passwords.hash(clave));
}

And to sign in with Google, Microsoft or GitHub, OAuth brings the complete flow with PKCE and signature verification of the id_token.

OAuth 2.0Java
OAuth google = OAuth.google(id, secreto, "https://mi-sitio/auth/google/vuelta");

@Get("/auth/google")
public Result entrar(Context ctx) {
    return Result.redirectExternal(google.autorizar(ctx).url());
}

@Get("/auth/google/vuelta")
public Result vuelta(Context ctx) {
    var identidad = google.intercambiar(ctx);
    ctx.session().regenerateId();
    ctx.session().set("usuario", identidad.correo());
    return Result.redirect("/panel");
}
The state is not decoration

autorizar(ctx) stores the PKCE verifier and a random state in the session; intercambiar(ctx) reads them back, compares the state against the one the provider returns in constant time, and clears it before redeeming the code.

Without that check there is a concrete attack: someone starts the flow with their account, keeps the code, and gets the victim to visit the callback URL. The victim ends up inside the attacker's session, and anything they save there — an address, a document, a card — lands in someone else's account. That is why the step lives inside the framework and not in the example everyone copies.

For several instances, or so that sessions survive a deployment, the store goes into a table. With the in-memory one —the default— every deployment throws everybody out.

Shared sessionsJava
ServerOptions.builder()
    .sessionStore(JdbcSessions.of("cero_sesiones").createTable())
    .sessionMaxLifetime(Duration.ofHours(12))   // a lifetime cap, not just inactivity
    .build();

Tasks and cache

Work outside the request: fire and forget, wait for a result, repeat every so often or follow a cron expression. Each task runs on its own virtual thread, so blocking inside one does not cost a platform thread.

TasksJava
Tasks tareas = Tasks.start();

tareas.run(() -> correo.enviar(aviso));                  // and forget about it
var futuro = tareas.submit(() -> informe.generar());       // with a result
tareas.every(Duration.ofMinutes(5), () -> sondear());
tareas.cron("0 3 * * *", () -> respaldo());                // at three in the morning

And for whatever is expensive to compute and changes little, a cache with per-entry expiry:

Cache and EventsJava
Cache<String, List<Noticia>> portada = Cache.of(Duration.ofMinutes(10));
List<Noticia> ultimas = portada.get("portada", clave -> noticias.ultimas(6));

// Event bus: whoever publishes does not know who is listening.
eventos.publish(new NoticiaPublicada(id));

@Listens
public void alPublicar(NoticiaPublicada evento) {
    portada.invalidate("portada");
}

Testing

cero-test is the new module in 0.7.0, and it is already on Maven Central. It boots your application on a free port, asks it for something with a client that keeps cookies, and asserts on the response. Before it existed, every project wrote its own assertions by hand and copied the Maven wiring by reading our pom.xml.

pom.xmlXML
<dependency>
    <groupId>dev.ginit.cero</groupId>
    <artifactId>cero-test</artifactId>
    <version>0.7.0</version>
    <scope>test</scope>
</dependency>

It drags in nothing outside the JDK. cero-data is optional —only TestDatabase needs it— so an application without a database never sees it.

A complete example

TareasTest.javaJava
import cero.test.TestClient;
import cero.test.TestResponse;
import cero.test.TestServer;
import java.util.Map;

public class TareasTest {

    public static void main(String[] args) {
        // App.app() returns the configured Cero, the same one main() boots
        try (TestServer app = TestServer.start(App.app())) {
            TestClient cliente = app.client();

            cliente.get("/api/tareas").ok().contentType("application/json");

            TestResponse creada = cliente.post("/api/tareas",
                    Map.of("titulo", "Terminar la web", "prioridad", "alta"));
            creada.status(201)
                  .json("titulo", "Terminar la web");

            cliente.post("/api/tareas", Map.of("titulo", "x"))
                   .status(422)
                   .contains("titulo");

            cliente.get("/api/tareas/9999").status(404);
        }
    }
}

The operating system picks the port, so two modules testing at the same time do not collide. close() closes the clients it handed out and stops the server.

The session, which is what breaks most

The client keeps cookies and does not follow redirects: a successful login answers 302 and that response is exactly the one the test wants to look at. Every client() gets its own cookie jar, that is, its own session.

Log in and stay inJava
TestClient cliente = app.client();

cliente.get("/yo").status(401);
cliente.form("/acceso", Map.of("usuario", "ada", "clave", "secreta"))
       .status(302)
       .cookie("CEROSESSION");
cliente.get("/yo").ok().json("usuario.nombre", "Ada");

The same test over HTTP/2

By default the client negotiates the version. http1() and http2() pin it, which is how you check that something works the same through both doors.

Session over HTTP/2Java
TestClient cliente = app.client().http2();
TestResponse portada = cliente.get("/").ok();

if (portada.version() != HttpClient.Version.HTTP_2) {
    throw new AssertionError("the server did not speak HTTP/2");
}

cliente.form("/tareas", Map.of("_csrf", token(portada.body()), "titulo", "Alta"))
       .status(302);   // the session survives the second request
Why that test is written down

In 0.7.0 the session cookie was lost over HTTP/2: the first request opened a session and the second one arrived as a stranger. A test that only goes over HTTP/1.1 sees none of that. version() exists so you can assert which version the response actually came over, instead of trusting that you asked for it.

With a database

TestDatabase opens a throwaway database and registers it as the default source, so the application under test uses it without touching anything. migrate applies the whole batch against it and fails naming the broken migration.

TestDatabaseJava
try (TestDatabase db = TestDatabase.of("jdbc:h2:mem:pruebas");
     TestServer app = TestServer.start(App.app())) {

    int aplicadas = db.migrate(Migrations.from(Path.of("db/migraciones")));

    app.client().get("/usuarios").ok();
}

TestDatabase.of(String jdbcUrl) takes the default source; TestDatabase.of(String source, String jdbcUrl) registers a named one. pool() and source() return what was registered.

How they are run

Cero does not use JUnit: every module has a class with a main that runs its tests and exits with a non-zero code if any of them fails, and exec-maven-plugin launches it in the test phase. You copy it from the pom.xml of cero-test, changing the class name.

If your project does use JUnit, none of that is needed: TestServer and TestDatabase are AutoCloseable and fit into a @BeforeAll/@AfterAll or a try-with-resources.

Migrations and rows

Migrations are numbered .sql files, and run() applies the ones that are missing and records each of them with its fingerprint:

MigrationsJava
Migrations migraciones = Migrations.from(Path.of("db/migraciones"));
// or Migrations.fromClasspath("db/migraciones") if they live inside the jar

int aplicadas = migraciones.run();          // only the missing ones
List<String> yaEstan = migraciones.applied();

An already applied migration that gets corrected

The fingerprint is what stops an already applied file from changing behind everyone's back. But sometimes the correction is legitimate —a comment, a misspelt name inside the SQL itself— and does not alter what that migration left in the schema. At that point startup stops in every environment at once, and until 0.7.0 the only way out was editing the bookkeeping table by hand.

repair()Java
// Recomputes the fingerprints and rewrites the ones that changed. It re-runs nothing.
List<String> reparadas = Migrations.from(Path.of("db/migraciones")).repair();

It returns the names whose fingerprints were rewritten. It is only valid if the correction does not change the resulting schema: if it does, what you need is a new migration —repair() would leave the database without the change and the record saying it is there.

So the failure shows up in continuous integration

verify(String) applies the whole batch against another source —an empty, throwaway database— and returns the result instead of throwing. That way a broken batch shows up in the pipeline and not while bringing up a new environment, which is when there is least time.

verify()Java
DataSources.register("ensayo", Pool.to("jdbc:h2:mem:ensayo").build());

Migrations.Verificacion resultado =
        Migrations.from(Path.of("db/migraciones")).verify("ensayo");

if (!resultado.correcta()) {
    throw new AssertionError(resultado.resumen());
}
record VerificacionWhat it carries
boolean correcta()Whether the whole batch applied
int aplicadas()How many ran before stopping
String migracion()The one that broke, or null
String fallo()The error message, or null
String resumen()Both things in one line, for the log

If you already use cero-test, TestDatabase.migrate(…) does this on its own: it calls verify against its own database and throws with the name of the broken one.

A row is a map

Row implements Map<String,Object>, read-only and with case-insensitive column lookup. What that solves: a Row nested inside a response is serialized as a JSON object, instead of falling into getter introspection and forcing you to convert it by hand with toMap().

RowJava
Row fila = Db.open().one("select id, titulo, creada from tareas where id = ?", id);

return Map.of("tarea", fila, "servidor", nombre);   // comes out as {"tarea":{…}}

fila.get("TITULO");        // the column is looked up ignoring case
fila.text("titulo");       fila.date("creada");      fila.as(Tarea.class);
Breaking change: Row.put is no longer Row's

A row is built with Row.of(key, value, …) or Row.from(map). The put that remains is the one from the Map contract, and like the rest of the write operations it throws UnsupportedOperationException.

Code that chained —Row.of().put("a", 1).put("b", 2)— or that stored the result in a Row variable stops compiling: Map's put returns the previous value, not the row.

SQL dates in JSON

The three java.sql types inherit from java.util.Date, so they used to fall into its branch and come out as instants: 19:00 turned into 1970-01-02T00:00:00Z and a date moved a day forward on its way to UTC. Now each one comes out as what it is.

TypeComes out asExample
java.sql.Dateyyyy-MM-dd"2026-03-14"
java.sql.TimeHH:mm:ss"19:00:00"
java.sql.TimestampISO-8601 instant"2026-03-14T19:00:00Z"
java.util.DateISO-8601 instant"2026-03-14T19:00:00Z"

This is what saves you from filling your queries with to_char(…) so the JSON reads well: a date and a time from the database now reach the client with the shape they have in the database.

Configuration and environment

loadConfig() reads, in this order, application.properties from the classpath, the same file next to the process, the CERO_* variables and the -Dcero.* system properties. The last one wins.

StartupJava
Cero app = Cero.app()
                .loadConfig()          // or .config(Config.load("mi.properties"))
                .controllers(TareasController.class);

int tope = app.configuration().getInt("limite.peticiones", 100);

app.start();                           // this is where the warnings come out

A variable is translated by dropping the prefix, lowercasing the name and turning _ into dots: CERO_SERVER_PORT is server.port.

The startup warnings

At startup, once everyone has asked, Cero goes over the CERO_* variables that have not ended up in any key anyone reads, and warns. There are three cases:

What happensWhat you see on the console
The variable matches no known keyCERO_SERVER_PORTT no corresponde a ninguna clave conocida (server.portt)
The key is camelCase and the environment cannot reach itCERO_SERVER_BEHINDPROXY no se aplica: la clave es server.behindProxy, en camelCase, y el entorno no distingue mayúsculas
The application never calls loadConfig()CERO_SERVER_PORT no se leen: la aplicación no llama a loadConfig()
Why a warning and not a footnote

A misspelt variable did not fail: it came in with the default value, silently. In production that meant the session cookie going out without Secure because behindProxy never got switched on, and the rate limiter counting everyone together because trustProxy never arrived either. A deployment that starts perfectly and does not do what the configuration file says is the worst place to hide that.

The list of known keys is not maintained by hand: asking for a key declares it, even if it is not there. That is why the pass happens at the end of startup and not before.

The camelCase case has no way back from the environment, because the translation lowercases the name. That key goes in application.properties or as a system property, which does keep the capitals: -Dcero.server.behindProxy=true.

Behind a proxy

Cero speaks HTTP/1.1 and HTTP/2. For HTTP/3 and automatic certificates you put nginx or Caddy in front, which also absorbs slow connections. It is the recommended way to deploy it.

HTTP/2, and how to turn it off

It ships on. An application never notices: it gets the same Request and the same Response as on HTTP/1.1. You come in through three doors: both h2c ones in the clear —prior knowledge, or Upgrade: h2c from an HTTP/1.1 request—, which is what a proxy terminating TLS for you speaks, and ALPN over TLS, the only one a browser will use: none of them speaks h2c.

HTTP/1.1 onlyJava
ServerOptions.builder()
    .http2(false)     // ALPN does not announce h2, and h2c is not accepted
    .build();

Turning it off makes sense in one concrete place: an intermediary that chokes on h2c, or a measurement that wants to compare both versions without the client negotiating on its own. PUSH_PROMISE is announced as disabled —it is deprecated— and PRIORITY is read and discarded, which is what RFC 9113 allows.

Two things you have to declare

Behind a proxy, the request arrives from the proxy itself and in plain text. If nobody tells it otherwise, the application believes nobody is using HTTPS —and does not mark the session cookie as Secure— and sees everyone coming from the same address, so the rate limiter counts them all together and the first to hit the cap blocks the whole site. 

ServerOptions.builder()
    .behindProxy(true)                  // honours X-Forwarded-Proto
    .trustProxy("127.0.0.1", "::1")       // and X-Forwarded-For, only from there
    .build();

The trust list is neither optional nor cosmetic: believing those headers wherever they come from lets anyone claim to be another address, and with that they slip past the limiter and pollute the logs.

And static files with their cache directive, because otherwise the browser revalidates more than it needs to:

Static filesJava

With React, Svelte or Vue

Cero does not force you to use its template engine. It can serve JSON and nothing else and let the frontend paint it, which is the normal thing today. Both ways live side by side in the same application: some routes return views and others JSON.

In development · two servers

The frontend on its own server —5173 for Vite, 3000 for Next— and Cero on its own. Since they are different origins, you have to open CORS for that port and only for that one:

DevelopmentJava
Cero.app()
   .use(Cors.allowing("http://localhost:5173"))
   .controllers(ApiController.class)
   .start();

In production · a single artefact

You build the frontend, copy its output into the resources, and out comes one jar that serves both. No nginx in front to join them, no two deployments.

One jar with everythingJava
Cero.app()
   .controllers(ApiController.class)          // /api/... returns JSON
   .fallback(StaticFiles.fromClasspath("front").spa()
                        .cacheControl("public, max-age=31536000, immutable"))
   .start();
What spa() does and why it is needed

An application that routes on the client —React Router, Svelte's router— does not have one file per route: only index.html exists. Without spa(), going straight to /panel/usuarios/7 would give a 404 and the application would only work when navigating from the home page.

With spa(), a route that does not exist as a file returns index.html and the browser decides what to paint. But only for page routes: a missing .css or .png still gives a 404 — handing them the home page's HTML turns an obvious error into one that takes an hour to find.

If your frontend generates one file per route —Next.js static export, Astro, Hugo— you do not need spa(): /nosotros finds nosotros/index.html on its own.

16

Real time

Two ways, and nearly always you want the first.

Server-sent events · one direction

The server sends when there is something, instead of the browser asking every two seconds. It is ordinary HTTP: it crosses proxies with nothing to configure and the browser reconnects on its own. For a dashboard, a progress bar or a notification, it is exactly what is needed.

ServerJava
@Get("/eventos")
public void eventos(Context ctx) throws InterruptedException {
    try (Sse eventos = Sse.open(ctx.response())) {
        while (eventos.abierto()) {
            eventos.send(Json.write(metricas.snapshot()));
            Thread.sleep(1000);
        }
    }
}
BrowserJavaScript
const eventos = new EventSource('/eventos');
eventos.onmessage = e => pintar(JSON.parse(e.data));
Why that loop is not a problem

That while keeps the thread inside for as long as the dashboard is open. With platform threads it would be unworkable —a hundred dashboards, a hundred blocked threads— but Cero serves each connection on its own virtual thread: a hundred dashboards are a hundred virtual threads, costing a few hundred bytes each. That is why here you can write blocking code without paying for it.

This site's dashboard uses it: the numbers you see are pushed by the server every second.

WebSocket · both directions

For when the browser also has to talk — a chat, a shared editor, a game. It costs a separate protocol and a configured proxy; if you only need to receive, do not use it.

WebSocketJava
.routes(r -> r.ws("/chat", socket -> {
    socket.onMessage(texto -> socket.send("eco: " + texto));
    socket.onClose(() -> log.info("se fue"));
}))
Same origin only, and it is not optional

A WebSocket carries the site's cookies and the browser's same-origin policy does not protect it: with nothing checked, any site a user visits can open a channel against your application with that user's session and read whatever comes out of it. It is CSRF, but with a reply.

Cero compares Origin against Host during the handshake and answers 403 when they differ. A client that is not a browser sends no Origin and passes: that header is set by the browser and page JavaScript cannot change it, so its absence means there is no page involved.

If your frontend lives on another domain, or a reverse proxy rewrites Host with the internal address, declare the origins: WebSockets.accept(request, response, handler, Set.of("https://app.pe")). The 403 names both values it compared, so this is not debugged blind.

On "reactive programming"

Cero has no Flux, Mono or anything of the sort, and that is a decision. That style exists to avoid blocking platform threads, which are expensive. With Java 21's virtual threads they stop being expensive: you can write ordinary top-to-bottom code that blocks — and the performance is the same, without the cost of chaining operators or debugging unreadable stack traces. Same capability, another road.

Multiple languages

Texts live in .properties on the classpath: one base file and one per language.

src/main/resourcesFiles
mensajes.properties        # the base language
mensajes.en.properties
mensajes.qu.properties
StartupJava
Cero.app()
     .messages(Messages.from("mensajes", "en", "qu").base("es"))
     .start();

The languages have to be named. The classpath cannot be listed reliably when the application runs inside a jar, so discovering them automatically would work in development and fail exactly at deploy time.

In a controllerJava
public Object saludar(Context ctx) {
    return Result.text(ctx.t("saludo", nombre));   // «Hello, Richar»
}

The language comes from Accept-Language, and the quality factor is respected: fr;q=0.2,qu;q=0.9 answers in Quechua even though French comes first. A regional tag falls back to its language —es-PE uses es—. To pin it by hand, ctx.idioma("en").

In templates

The t map arrives on its own. You do not put it in each controller's model, and that is exactly why it exists as a global: forgetting it in one single controller would leave that page untranslated, and nobody would notice until a user complained.

plantilla.htmlTemplate
<button>{{ t.guardar }}</button>

If the model carries a key with the same name as a global, the model wins. The other way round, adding a new global would silently mask a value in a template that already worked.

Why not ResourceBundle

ResourceBundle falls back to the system language when it cannot find a key. That makes the same deployment answer differently depending on how the server is configured: a bug that reproduces on nobody's machine. Here the fallback chain is written down —requested language, base language, the key itself— and is the same everywhere.

A missing text returns the key and does not throw: a half-translated page still serves. But it warns on the console once per key, not on every request.

Regions that repaint themselves

Mark a region in the template and the server repaints it whenever it wants, without you writing a line of JavaScript.

plantilla.htmlTemplate
<div data-live="carrito">
  {{ include "carrito.html" }}
</div>
<script src="/cero/live.js"></script>
From anywhere on the serverJava
Live live = Live.enabled();

Cero.app()
     .views(plantillas)
     .live(live)          // needs views() first
     .start();

live.push("carrito", "carrito.html", modelo);
What travels down the wire is HTML, not JSON

That is the whole reason this exists. The browser does not have to know how to render anything, so there is no second copy of your templates written in JavaScript to drift out of sync with the real ones. There is one template and it lives on the server.

The client is forty lines served by the framework itself at /cero/live.js. No build step, no node_modules, nothing to install.

  • With nobody watching, nothing is rendered. Painting a template only to find out afterwards that there were no recipients is wasted work, and in a task pushing every second it shows.
  • It reconnects on its own, backing off up to 15 seconds. A connection that dies quietly is worse than none: the page sits there showing stale data without saying so.
  • The channel only pushes. The only thing the browser sends is the names of the regions on its page. It accepts no commands.
  • live.pushHtml(region, html) sends ready-made HTML, if you build it yourself.

Who may listen to a region

The browser sends the region name, because the server does not know what is painted on that page. As long as the region carries the same thing for everyone — a scoreboard, a quote, the state of a queue — that is exactly what you want. The moment it carries one person's data, you have to say who may hear it: a name like orders-42 is guessable.

Private regionsJava
Live live = Live.enabled().autorizar((peticion, zona) -> {
    if (!zona.startsWith("orders-")) {
        return true;                      // public regions, for everyone
    }
    var sesion = peticion.session(false);
    return sesion != null
        && zona.equals("orders-" + sesion.get("usuario"));
});

The guard runs once per region per connection. A rejected region is not registered and the socket stays open for the rest: losing one region need not break the whole page.

  • Same origin only. The handshake compares Origin against Host. Without it, another site could open this channel with the session cookie of anyone who visits it. If your frontend lives on another domain, or a proxy rewrites Host, declare it with live.origenes("https://panel.ginit.dev").
  • Per-connection caps. Up to 32 regions and 64 characters per name. A real page has three or four; the cap is there so nobody fills the server's memory by inventing names.
  • The map returns to zero. When the last listener leaves, the region disappears from the server instead of lingering as an empty set forever.

Health

StartupJava
Cero.app()
     .health(Health.checks()
         .ready("bd", () -> db.ping())
         .ready("correo", () -> mail.reachable()))
     .start();
PathSays
/cero/vivoThe process answers. Nothing more
/cero/listoIt can also serve: every check passes. 503 if any fails
They are not the same, and confusing them does harm

A process can be alive and unable to serve: the database is not answering, a service it depends on is down. If the supervisor restarts over what was only a slow database, it turns a passing problem into an outage. And if it never restarts, a hung process stays hung.

That is why /cero/vivo takes no checks: if it accepted one, it would stop measuring what it claims to measure.

/cero/listo answers 503, not a 200 with a body saying «bad»: supervisors read the status code, not the body. A check that throws counts as a failure and its message goes inside — swallowing the exception would leave a «not ready» with no explanation exactly when you need one.

If the route is served to the internet

That detail is exactly what you want on an internal network and exactly what you do not want in plain sight: a connection failure's message carries your database host and port inside it. With publico() only the status code and the state remain.

ExposedJava
Cero.app()
     .health(Health.checks().publico()
         .ready("bd", () -> db.ping()))
     .start();

// 503 with {"estado":"no listo"} — no names, no messages

Not publishing it at all is still better: if the supervisor runs on the same machine, a deny in the proxy for /cero/listo keeps the full detail for you and gives it to nobody else.

Untrusted input

Most of the time you need nothing: templates escape by default. A {{ comment }} with <script> inside comes out as visible text, not as a script. Not escaping has to be asked for on purpose, with {{ & content }}, and that is where your responsibility starts.

TemplateTemplate
{{ comentario }}      // escaped, the normal case
{{ & comentario }}    // raw: only if you already cleaned it

When the user has to be able to write in bold

A comment, a description, text from a rich editor: you want to keep <b> and <a> and drop everything else. That is Sanitize.

ControllerJava
String limpio = Sanitize.html(ctx.form("comentario"));
String resumen = Sanitize.text(limpio);            // no tags at all
String archivo = Sanitize.filename(parte.filename());
Nothing from the input reaches the output as-is

That is what separates this from a filter. The previous version removed the dangerous parts with regular expressions and let the rest through; that is a blocklist, and an HTML blocklist always has one more hole. The one that broke it was <svg/onload=alert(1)>: the pattern that stripped handlers required a space before on…, and a slash is not one, so the tag came out intact.

Now the input is read, what is there is recognised, and the output is written again from scratch. An attribute that is not on the list is not examined to see whether it is dangerous: it is not emitted. That is why onload is dropped whether it follows a space, a slash, a newline or a quote.

InOut
<p>hi</p><p>hi</p>
<svg/onload=alert(1)>nothing
<script>alert(1)</script>nothing, contents included
<unknown>text</unknown>text
<a href="jav&#97;script:x">t</a><a>t</a>
<p>unclosed<p>unclosed</p>
  • URLs are judged the way the browser will read them. Entities are decoded and control characters stripped first: jav&#97;script: and java&#9;script: are both javascript: as soon as the browser reads them, and both are dropped. http, https, mailto, tel and any relative path pass.
  • Links come out with rel="nofollow noopener noreferrer". A link from outside does not lend the site's reputation nor hand over anyone's window.opener.
  • The output always closes. Anything left open is closed at the end and an orphan closing tag is discarded: broken input cannot eat the rest of the page.
  • Sanitize.text(…) leaves no tags. That is what you want for a summary, an email subject or a search index.
  • Sanitize.filename(…) keeps only the last path segment: ../../etc/passwd is passwd.

For the rest of the input — lengths, formats, ranges — there is validation, which is where it belongs: what does not comply never reaches the controller.
