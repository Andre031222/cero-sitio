Migrating

Taking an application from LuxCore 0.2.x or 0.3.x to Cero 0.6.0. The script does nearly everything; there are three things it cannot do, and all three show up after you deploy.

01

No rush

The applications you do not migrate keep working. Maven artifacts are immutable: lux:lux-core:0.3.0 is still in your ~/.m2 and inside every deployed jar. Renaming the framework does not reach in there and change anything.

You can migrate one, leave the other five as they are for months, and nothing happens. The v0.3.0 tag is still there: if one day an old application has to be rebuilt on a clean machine, ./lux install from that tag regenerates the old artifacts.

How to do it

One at a time. With production involved, that is how you keep a problem to one application instead of six.

02

Before you touch anything

1 · Install Cero 0.6.0

In the Cero repositorysh
./cero install          # builds, tests and installs into ~/.m2

2 · Leave the application's git tree clean

In your applicationsh
cd ../mi-app
git status               # nothing may be left uncommitted

The script refuses to run if there are uncommitted changes, and that is on purpose: git itself is the backup. git diff shows everything it touched and git checkout . undoes all of it. No need to go copying folders around.

3 · Rename the migrations table

This goes before you start the application

If your application uses Migrations from cero-data, stop and read. The framework records in a table which migrations already ran. It was called lux_migraciones and is now cero_migraciones. If you start without renaming it, Cero does not find it, assumes none ever ran, and runs them all again.

That does not fail at compile time. It fails against your database.

Before startingSQL
ALTER TABLE lux_migraciones RENAME TO cero_migraciones;

Same with the sessions table, if you use JdbcSessions and kept the default name:

Only if you use JdbcSessionsSQL
ALTER TABLE lux_sesiones RENAME TO cero_sesiones;

If you passed a name of your own —JdbcSessions.of("my_sessions")— there is nothing to do.

03

Migrate

In the Cero repositorysh
./cero migrar ../mi-app --probar    # shows what would change, touching nothing
./cero migrar ../mi-app             # applies it

It walks .java, pom.xml, .properties, .yml, .yaml, .env and .conf. It skips target/, build/, .git/ y node_modules/.

Check it

In your applicationsh
cd ../mi-app
git diff                 # review what changed
mvn test                 # and that it still passes
04

What the script cannot do

Three of them. None fails at compile time, and all three show up after you deploy — which is the worst moment to find out.

The session cookie changed name

LUXSESSION becomes CEROSESSION. Every user's browser keeps sending the old one, which the new application no longer recognises.

What follows

On deploy, everyone who was signed in has to sign in again. Nothing is lost, but deploy when it does not get in the way, and warn people if it is an application with users at work in it.

The metrics changed name

BeforeAfter
lux_requests_totalcero_requests_total
lux_request_errors_totalcero_request_errors_total
lux_request_duration_mscero_request_duration_ms
lux_uptime_mscero_uptime_ms
/lux/metrics/cero/metrics
/lux/metrics/prometheus/cero/metrics/prometheus
What follows

Prometheus scrapes a path that no longer exists, and the Grafana panels query metrics that stopped being emitted. The panels do not error: they go empty, which is worse, because it looks like the application is getting no traffic. You have to update prometheus.yml and the panel queries.

The deployed configuration, not just the one in the repository

The script changes the .properties that live inside the application. If the server has a separate application.properties, or LUX_* variables in systemd or docker-compose, those you change by hand.

On the serversh
grep -rn 'LUX_\|lux\.' /etc/systemd/system/mi-app.service /opt/apps/mi-app/
05

No compatibility layer

It was the obvious option: have Cero understand both names for a while. It was dropped on purpose.

Only six applications use the framework and they are all ours. Accepting both prefixes would mean carrying dead code forever in a project whose whole argument is having no ballast — and in practice nobody ever removes those layers. Converting six applications once is cheaper than carrying the debt indefinitely.

06

If something goes wrong

Undosh
git checkout .           # undoes the whole migration

And in the pom.xml, go back to the previous version. The old artifacts are still in ~/.m2 and the application builds as before, because they never stopped existing.

If you already renamed the tables and want to go all the way back:

Roll backSQL
ALTER TABLE cero_migraciones RENAME TO lux_migraciones;
ALTER TABLE cero_sesiones RENAME TO lux_sesiones;
07

Checklist

  • ./cero install — Cero 0.6.0 en ~/.m2
  • The application's git tree, clean
  • ALTER TABLE lux_migraciones RENAME TO cero_migraciones;
  • ALTER TABLE lux_sesiones RENAME TO cero_sesiones; (if it applies)
  • ./cero migrar ../mi-app --probar
  • ./cero migrar ../mi-app
  • git diff y mvn test
  • Server configuration: systemd, docker-compose, the production .properties
  • Prometheus and the Grafana panels
  • Warn that sessions close on deploy
